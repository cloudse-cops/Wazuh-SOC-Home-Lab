\## 2. Executive Summary

A controlled SSH brute-force simulation was performed against  
the monitored Ubuntu endpoint \`arman-VirtualBox\`.

Multiple failed SSH authentication attempts were generated  
against the \`arman\` account. Wazuh collected the authentication  
events and correlated the repeated failures, triggering Rule  
5763:

"sshd: brute force trying to get access to the system.  
Authentication failed."

The investigation found no successful SSH authentication  
during the examined time window and no evidence of account  
or system compromise.

The activity was part of a controlled cybersecurity lab  
and did not affect any production system.

\---

\## 3. Detection

Wazuh detected repeated failed SSH authentication attempts  
generated by the monitored endpoint.

Detection details:

\- Rule ID: 5763  
\- Rule Level: 10  
\- Frequency: 8  
\- Detection Type: SSH brute-force activity  
\- Decoder: sshd  
\- Source IP: 127.0.0.1  
\- Target Account: arman

The rule correlated repeated authentication failures within  
its configured detection window.

\---

\## 4. Attack / Test Scenario

A controlled SSH authentication test was performed against  
the local SSH service running on \`arman-VirtualBox\`.

An intentionally incorrect password was supplied repeatedly  
for the \`arman\` account.

The purpose of the simulation was to verify that:

1\. SSH generated authentication failure events.  
2\. Wazuh collected the events.  
3\. Wazuh SSH detection rules processed the events.  
4\. Repeated failures triggered the brute-force detection.

\## 7. Investigation Findings

The investigation established the following:

\- Multiple failed SSH authentication attempts occurred.  
\- The attempts targeted the \`arman\` account.  
\- The source of the controlled test was \`127.0.0.1\`.  
\- Wazuh successfully correlated the repeated failures.  
\- Rule 5763 generated a Level 10 brute-force alert.  
\- No successful SSH authentication was observed.  
\- No evidence of account compromise was identified.  
\- No evidence of system compromise was identified.  
\- The activity occurred entirely within the controlled lab.

\## 8. MITRE ATT&CK Mapping

\### Tactic

Credential Access

\### Technique

T1110 — Brute Force

\### Sub-technique

T1110.001 — Password Guessing

\### Rationale

The simulated activity consisted of repeated password  
authentication attempts against an SSH service. The observed  
behavior therefore corresponds to password guessing under  
the MITRE ATT&CK Brute Force technique.

\---

\## 10. Response

\### Detection

Wazuh generated an alert for the repeated SSH authentication  
failures.

\### Containment

The controlled test activity was stopped.

\### Investigation

SSH authentication logs and Wazuh alert data were reviewed  
to determine the source, target account, timeline, and outcome.

\### Recovery

No recovery action was required because the simulated activity  
did not result in successful access or system compromise.

\---

\## 11. Recommendations

For a production environment, repeated SSH authentication  
failures should be investigated for legitimacy and correlated  
with other endpoint and network telemetry.

Recommended controls include:

\- Monitor repeated SSH authentication failures.  
\- Investigate unexpected source IP addresses.  
\- Prefer strong authentication mechanisms such as SSH keys  
  where appropriate.  
\- Review exposed SSH services and restrict unnecessary access.  
\- Correlate authentication events with subsequent activity.  
\- Maintain centralized security monitoring and alerting.

\## 12. Lessons Learned

This investigation demonstrated the complete workflow from:

Detection → Alert Triage → Evidence Collection →  
Investigation → MITRE ATT&CK Mapping → Incident Response

The exercise also demonstrated that a security alert must  
be investigated in context. Repeated authentication failures  
were suspicious behavior, but the final investigation showed  
that the controlled activity did not result in successful  
authentication.
